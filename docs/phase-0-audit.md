## 1. 现有功能

### 1.1 页面结构

页面是一个无外部依赖的暗色单页，包含五块：

| 区块 | 现有内容 | 评价 |
|---|---|---|
| Hero | 标题“合租账单分摊器 / 第二次变更版”、规则说明 | 视觉基调可保留；需改为账本/账期上下文 |
| 01 居住信息 | 小林、阿哲、小周三个在住天数输入框 | 人员硬编码，需改为账本成员/入住记录 |
| 02 本月账单金额 | 电费、水费、宽带费、垃圾清运费四个金额输入框 | 账单类型和金额硬编码，需改为账期账单 |
| 03 新规则应承担金额 | 4×3 的分摊矩阵、每人合计、总账单 | 表格与金额展示可保留；计算移到服务端 |
| 04 历史已收与退补差额 | 每人历史已收、新应承担、差额、处理方式、差额合计 | 需重构为真实付款记录与正式结算快照 |

| 页脚 | 本地计算声明、计算日期、状态 | 需增加 API/版本信息，不能只显示本地状态 |

### 1.2 交互

- 3 个在住天数输入框，`min="0" step="1"`，默认 `18 / 30 / 30`。
- 4 个账单金额输入框，`min="0" step="0.01"`，默认 `287.65 / 96.40 / 89.00 / 20.00`。
- 任意输入触发 `input` 事件，页面即时重算：
  - 新规则应承担矩阵；
  - 每人新应承担合计；
  - 总账单；
  - 与“冻结历史已收”的差额和补缴/退款标签。
- 没有提交按钮、没有保存按钮、没有网络请求、没有 `localStorage`/`IndexedDB`。
- 页面标题带有“第二次变更版”，说明这是一次规则变更演示。

### 1.3 技术实现

- 单文件，HTML + 内嵌 CSS + 内嵌 IIFE JavaScript。
- 无第三方库、无字体/图片等外部资源、无网络请求。
- `window.__split` 暴露纯分摊函数，便于测试。
- 使用 `data-testid`、`data-person`、`data-bill`、`data-cents` 建立测试契约。
- 金额以整数“分”作为中间量；显示时用 `Intl`/`toLocaleString('zh-CN')` 格式化。

## 3. 现有计算逻辑

### 3.1 `split()` 函数

签名：

```js
split(totalCents, weights, fallbackWeights, remainderMode, ownerIndex)
```

处理步骤：

1. `totalCents` 非有限数按 0；`Math.trunc` 向零截断；取绝对值并记录符号。
2. 输出长度等于 `weights.length`；空数组按 1 个分摊对象处理。
3. 权重逐项归一化：只有“有限正数”保留，`NaN`、负数、非数字、缺失都变 0。
4. 主权重总和为 0 时尝试 `fallbackWeights`。
5. 主、备用权重都无效时，退化为每人权重 1。
6. 按 `amount * weight / sum` 求精确份额，先 `Math.floor` 到分。
7. `remainderMode === 'owner'`：全部剩余分加到 `ownerIndex`；非法下标回退到最后一人。
8. 否则 `spread`：按小数余数从大到小分配剩余分，余数相同按人员顺序。
9. 恢复金额正负号，返回整数分数组。

### 3.2 页面中的分摊策略

| 账单 | 新规则权重 | 零头处理 | 备用规则 |
|---|---|---|---|
| 电费 | 入住天数 | 全部归小周（下标 2） | 权重全零时按三人均分 |
| 水费 | 入住天数 | 全部归小周 | 同上 |
| 宽带费 | `[1,1,1]` 按户平摊 | 全部归小周 | 均分权重不会全零 |
| 垃圾清运费 | `[1,1,1]` 按户平摊 | 全部归小周 | 同上 |

### 3.3 “历史已收”基线

`freezeHistoricalReceipts()` 在页面脚本首次执行时调用一次：

- 读取**当时输入框里的四笔金额和三个人天数**；
- 对四笔账单**全部按入住天数**分摊；
- 用旧规则 `spread` 分散零头；
- 把四笔结果累加到 `frozenPaid`；
- 之后输入变化只重算新规则，不再改 `frozenPaid`。

注意：旧页面中的“历史规则”并不是“宽带/垃圾按户平摊”，而是**四笔全部按入住天数**。这与新规则有明确差异。

### 3.4 差额

`差额 = 新应承担金额 − 历史已收金额`

- 正数：需补缴（红色）；
- 负数：应退款（绿色）；
- 零：无需调整。

页面把三人差额相加，显示为“退补守恒”，静态文案称应为 `¥0.00`。

### 4.4 修改金额后的异常

把电费从 `287.65` 改成 `300.00` 后：

- 新应承担总额增加 `12.35`；
- 冻结基线不变；
- 三人差额合计变成 `¥12.35`；
- 页面静态文案仍写“三人差额合计应为 ¥0.00（不产生额外收入或支出）”，只是数字变红。

这不是数学错误，而是界面把“结算差额合计”错误地描述成恒为零。真实收款总额与新应承担总额本来就可以不同；需要解释差额来源，而不是强制为零。

## 5. 发现的缺陷与风险

| 编号 | 严重度 | 领域 | 问题 | 证据/影响 |
|---|---|---|---|---|
| D01 | 阻断 | 历史实收 | 没有真实收款录入；自动基线被文案称为“已冻结” | 文案称“历史收款基线已冻结”，但没有编辑入口；实际值是按默认输入算出来的示例 |
| D02 | 阻断 | 持久化 | `frozenPaid` 仅存在内存 | 刷新、换浏览器、换设备后所有输入和基线消失；正式账目不可依赖 |
| D03 | 阻断 | 数据模型 | 无用户、账本、账期、规则版本、付款、结算、审计表 | 无法多人访问、数据隔离、留痕或恢复 |
| D04 | 高 | 结算校验 | “差额合计应为 0”的静态声明不成立 | 改电费为 300 后实测 `¥12.35`，页面变红但不解释 |
| D05 | 高 | 输入校验 | 负数、三位小数、非整数天数、空值未拒绝 | 实测输入 `1.005` 得到 `100` 分；程序化输入 `-10.00` 后显示负账单且状态仍为“核对通过” |
| D06 | 高 | 迁移差异 | 旧基线四笔全部按天数、spread；新规则宽带/垃圾按户、owner | 若不记录差异，会把旧规则的错误分摊当成真实历史 |
| D07 | 高 | 算法实现 | 以 `Number` 浮点比例计算，不是严格整数运算 | 接近 `MAX_SAFE_INTEGER` 的合法整数分案例出现 1 分误差；正常金额未复现 |
| D08 | 高 | 权限/审计 | 无登录、无权限、无审计 | 任何能打开文件的人都能修改；无法知道谁改了什么 |
| D09 | 中 | 数据恢复 | 无备份/导出 | 浏览器数据清除即不可恢复 |
| D10 | 中 | 并发 | 无版本/锁 | 多人同时编辑会互相覆盖 |
| D11 | 中 | 账期 | 无月份/账期概念 | 所有输入只有一个“本月”，无法保留历史月份 |
| D12 | 中 | 零头归属 | 小周写死为数组下标 2 | 人员调整、成员退出、规则变化时容易错位；没有账面归属字段 |
| D13 | 中 | 可访问性/体验 | 无保存反馈、无错误提示、无确认；状态仅颜色变化 | 用户无法判断是否已保存；红/绿对色觉障碍用户不友好 |
| D14 | 低 | 安全 | 内联脚本、无 CSP；金额只用 `textContent` 渲染 | 当前无 XSS 注入点，但升级为聊天/备注后必须建立 CSP 和输出编码 |
| D15 | 低 | 日期 | 只显示本地日期，无时区/账期边界 | “本月”在跨时区或月初结算时可能歧义 |

### 5.1 关于“历史已收”的关键判断

旧页面的“历史已收”不是用户录入的数据，也没有任何持久化。它是由当前 DOM 的默认值计算出来的。因此：

1. **不能把它导入为 `payments` 真实收款记录。**
2. 迁移时应把它作为“旧规则示例/待核对建议值”展示，明确标注“未确认”。
3. 正式启用前必须由管理员逐人、逐笔录入实际收款，并二次核对。
4. 如果用户曾经在旧页面改过输入，那些修改没有被保存，无法自动恢复；只能在迁移说明中告知用户重新录入。

### 5.2 关于零头归属

旧页面用 `ownerIndex = 2` 写死小周。新系统必须：

- 在规则版本中存 `remainder_owner_person_id`，而不是数组下标；
- 在分摊明细中存 `is_remainder_owner` 和 `remainder_cents`；
- 在结算快照中冻结当时的零头归属人；
- 人员排序、成员增减不影响历史归属。

### 5.3 关于金额算法

旧 `split()` 在小额场景下守恒，但使用 `amount * (weight / sum)` 的浮点比例。阶段 2 必须改为：

- 用整数除法和余数分配（Python 任意精度整数）；
- 最大金额设上限（建议单笔不超过 10 亿元，即 `100_000_000_000` 分）；
- 所有输入先规范化为整数分；
- 禁止 `float` 参与金额累加；
- 每笔账单分摊后校验 `sum(shares) == total_cents`。

## 6. 迁移决策

### 6.1 必须保留

- 暗色视觉语言、卡片化布局、响应式表格；
- 人民币两位小数格式、负数显示、`data-cents` 契约；
- 三列人员、四列账单的桌面布局；
- `data-testid`、`data-person`、`data-bill` 命名；
- “整数分、逐笔守恒、零头归小周、差额 = 新应承担 − 历史实收”的业务表达；
- 旧版文件本身（只读存档，不覆盖）。

### 6.2 必须重构

- 计算从前端移到后端确定性引擎；前端只展示服务端结果。
- 历史基线改为真实 `payments` 流水。
- 规则从硬编码改为版本化规则。
- 账期、账本、人员、权限、审计全部进数据库。
- 输入校验、错误提示、保存反馈、确认流程。
- 金额解析改为严格的十进制定点解析。

### 6.3 必须替换

- `frozenPaid` 内存变量 → `payments` + `settlements` 快照。
- 固定数组 `people/bills` → 数据库实体。
- 差额静态“应为 0” → 按实际收款解释，并校验逐笔守恒。
- `ownerIndex` → 规则版本中的人员外键。
- 内联 IIFE → 静态 ES modules + `fetch` API 客户端。
- 自动基线 → 明确标注的“旧规则建议值”，需人工确认。

### 6.4 不允许的迁移方式

- 不得把旧页面自动基线静默写成真实收款。
- 不得为了新规则而覆盖旧页面文件。
- 不得删除旧版 DOM 标记后不提供替代测试标记。
- 不得只迁移计算结果而不迁移“差异说明/零头归属/历史版本”语义。

## 7. 旧页面与目标业务规则对照

| 业务规则 | 旧页面 | 目标系统 |
|---|---|---|
| 电费、水费按入住天数 | 是 | 规则版本 `days` |
| 宽带按户平摊 | 新规则是；旧基线否 | 规则版本 `equal_household`，历史基线单独冻结 |
| 垃圾按户平摊 | 新规则是；旧基线否 | 规则版本 `equal_household` |
| 零头归小周 | 是，但写死下标 | 规则版本人员外键 + 明细字段 + 快照 |
| 整数分 | 中间量是整数，比例用浮点 | Python 整数除法/余数 |
| 逐笔守恒 | 正常金额通过 | 单元/属性测试 + 服务端校验 |
| 权重全零备用规则 | 均分 | 规则版本显式 `fallback_method`，测试覆盖 |
| 规则版本控制 | 无 | `rule_versions` + `rule_version_items` + 预览/确认 |
| 历史实收不被覆盖 | 内存冻结，刷新丢失 | `payments` 只追加；结算快照冻结 |
| 正式结算保存规则/份额/实收/差额 | 无 | `settlements` + `settlement_lines` + JSONB 快照 |
| 规则修改先预览再确认 | 无 | 草稿版本 + 预览哈希 + 管理员激活 |
| 修正留审计 | 无 | `audit_logs`；冲正记录 |

## 8. 安全与质量观察

- 当前页面无登录，不能直接暴露到公网。
- 当前页面只使用 `textContent` 写数字，没有明显 XSS；新增备注、聊天和姓名后必须继续避免 `innerHTML` 拼接用户内容。
- 当前页面无网络请求，因此没有 CSRF；升级后必须加 CSRF。
- 当前无依赖，因此无供应链风险；升级后必须锁定依赖并做审计。
- 当前无日志，因此无敏感信息泄露；升级后必须对日志做脱敏。
- 当前页面没有 `<form>`，Enter 键不会提交；升级后应使用明确的表单/按钮和错误状态。
- 前端不得保存模型 API 密钥。

## 9. 待确认的业务问题

以下问题不阻塞阶段 1 设计，但在阶段 3 之前需要确认：

1. **历史实收语义**：`payments` 是“每个人为账期共同费用实际支付给房东/公共账户的金额”，还是“室友之间互相转账”的双边流水？本文设计按前者建模；后者需要双边记账。
2. **旧页面数据**：确认旧页面只有默认示例、没有真实数据需要自动导入；真实历史收款由管理员在启用前手工录入并核对。
3. **账期关闭流程**：建议 `open → locked → settled`；修正时管理员重新打开，生成新结算修订版，旧版保留并标记 `superseded`。
4. **负数账单**：建议 API 拒绝负数普通账单；冲正通过作废/重开或调整记录完成；引擎单元测试仍覆盖有符号金额。
5. **入住天数**：建议只允许 `0..31` 的整数天（v1 按月账期）；如确有半天需求，再改成 `numeric` 并定义舍入。
6. **注册方式**：建议默认关闭公开注册，由管理员创建/邀请；或开放注册 + 一次性邀请码。需要确认。
7. **零头归属人**：建议规则版本可配置，初始默认小周；历史版本冻结，不随人员变化。
8. **导出格式**：v1 建议 CSV；如必须 Excel，再加 `openpyxl` 导出 `.xlsx`。
9. **账单分类**：v1 是否只允许电费、水费、宽带、垃圾、其他五类；其他类别的默认分摊方式需要定义。
10. **部署环境**：是否有域名/公网服务器；若只在内网，HTTPS 仍建议用 Caddy 本地 CA 或内网证书。
